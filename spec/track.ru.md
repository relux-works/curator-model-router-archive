# Трек: роутинг моделей

Статус: **ЧЕРНОВИК**, 2026-09-23. Спецификация: `spec/model-routing.ru.md` (черновик, R1–R13, учтено независимое ревью). Роадмап: этап A0 внутри вехи M4 (это резолвер выбора агентов), остальное в вехе M8.

## Зачем

Сегодня модель для задачи выбирается из статического списка предпочтений на класс нагрузки. Роутер выбирает среди уже допущенных кандидатов по свидетельствам и записывает, почему; он никогда ничего не допускает, ничего не запускает и никогда не переключает учётные записи или выход в сеть.

## Как это сочетается с выбором агентов

Резолвер выбора агентов (`skill-project-management/.specs/drafts/agent-selection.md` §7) и есть CandidateResolver роутера: его жёсткие фильтры отвечают на вопросы «разрешено», «совместимо» и «доступно», а на шаге ранжирования работает стратегия роутинга. Потребности ролей из playbook'ов становятся признаками требований для роутера, предпочтения ролей — априорными оценками; жёсткие требования никогда не нарушаются. Свидетельства хранятся по роли или классу требований и по отпечатку исполнения.

## Вехи

| Этап | Что даёт | Когда |
| --- | --- | --- |
| A0 | один резолвер, совпадение с `config-order`, запись решения, приложение с контрактом | M4 (вместе с этапом S1 выбора агентов) |
| A1 | машинная половина: привязки из каталога, `bound_on_this_machine`, зависимые настройки | M4 |
| B | снимки свидетельств (адаптер Bug Hunt, собственные прогоны оценки), оценщик по правилам, детерминированный оценщик пригодности | M8, после доступности из M5 |
| C | смысловая оценка в теневом режиме (Jev или структурированная LLM, выбранная явно) | M8 |
| D | выбор по согласию при запуске, двухфазная проверка, доказательство фактической конфигурации | M8 |
| E | калибровка и измеренный выигрыш на собственных задачах | M8 |
